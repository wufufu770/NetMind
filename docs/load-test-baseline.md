# 并发压测基线

> 这份基线是**观测**，不是承诺。门禁 `load-test-no-loss` 只卡「零错误 + 数据不丢不坏」，
> 不卡延迟——CI runner 上 p99 抖动很大，拿它当门禁只会制造假红。
> 数据由 `python3 scripts/load_test.py` 实测产生。

## 采集环境

- 时间：2026-10-03
- 并发：20 线程 × 每线程 20 次
- 压测端：FastAPI TestClient（进程内，绕过网络栈，测的是应用层与存储层争用）
- 数据文件：独立临时目录，不碰真实数据

## 结果

| 场景 | 实发 | 错误 | p50 | p95 | p99 | max |
|---|---|---|---|---|---|---|
| 读：高频 GET telemetry | 400 | **0** | 133.71ms | 207.49ms | 238.05ms | 275.26ms |
| 读：高频 GET vendors | 400 | **0** | 170.45ms | 432.72ms | 626.98ms | 703.35ms |
| 写：并发 intent submit | 120 | **0** | 404.52ms | 696.04ms | 767.48ms | 879.89ms |
| 混合：读写并行 | 120 | **0** | 260.96ms | 1228.52ms | 1378.19ms | 1470.53ms |

压测后：数据文件完好、残留临时文件 0 个、服务自身观测计数 1041（= 1040 压测 + 1 预热），
4xx/5xx 均为 0。

## 读出来的三件事

**① 写比读贵 3–5 倍。** 并发 intent submit 的 p99 是 GET 的 3 倍多。原因清楚：每次写都要
过 `STORE` 的 `RLock` 并把整个 store 序列化落盘。RLock 只护进程内，所以**多进程部署
（多个 uvicorn worker 共享一个数据文件）会互相覆盖**——见下方风险。

**② 混合场景的 p99 最差。** 读写并行时 p99 达 1.38s，比纯读差 5.8 倍。写操作的锁持有
时间会阻塞同期的读。面板在轮询时如果撞上有人提交 intent，界面会明显卡一下。

**③ 零错误、零数据丢失。** 这是本次压测最该被记住的结论：原子写 + mkstemp 的组合在
并发下确实没写坏过任何一次。

## 已知风险（压测暴露但本轮未修）

- **多进程不安全**。`STORE` 的 `RLock` 只在单进程内有效。当前 uvicorn 默认单 worker
  尚可，但一旦用 `--workers N` 且共享同一数据文件，就会出现互相覆盖。
  商用前要么固定单 worker 并写进部署文档，要么换成有文件锁的实现。
- **写吞吐上限**。每次写全量序列化整个 store，数据量涨上去后写会线性变慢。
  当前上限 2000 日志 / 500 execution / 2000 遥测，超出即滚动丢弃。
- **压测端未经网络栈**。TestClient 绕过了 uvicorn/HTTP 解析，测的是应用层与存储层，
  不含真实网络往返。端到端延迟需在部署环境另行采集。

## 复现

```bash
python3 scripts/load_test.py --workers 20 --per-worker 20
python3 scripts/load_test.py --workers 8 --per-worker 8 --json    # 门禁用的规模
```

> 数字必须实发、实测。脚本早期版本打印的是 `workers × per_worker` 算出来的值，
> 而实际只发了 `per_worker` 条——报告了一个从没发生过的压测量。本项目禁止这种数字，
> 脚本现已改为实发实报并断言 `len(lat) == workers * per_worker`。
